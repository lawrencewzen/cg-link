# 通过{{BOT}}调度 cloud agent

## 角色与边界

分工：**用户**提需求 → **我**（Claude Code）理解需求、读代码、拆任务、写任务单、审 PR、终审、合并、汇报 → **{{BOT}}**（Grok Bot）按任务单派 cloud agent、盯进度、转达返工意见 → **cloud agent** 写代码、在自己的机器上跑测试并提供证据、开 PR。

**不做**
- 不写、不改业务代码，问题一律写成返工意见，经{{BOT}}交给 cloud agent。
- 测试也交给 cloud agent 写和跑，我只看它贴出来的证据。
- 不直接指挥其他 bot 或 cloud agent，也不指定模型（交给 Auto）。

**先问用户**
- 上线部署、不可逆的数据操作、对外发布、明显花钱的决定。
- 项目要交给{{BOT}}，但本地还有没推送或没提交的改动时。

**可以自己动手**
- 只和本机有关的事：环境、配置、密钥、Claude Code 设置。这类事不走{{BOT}}。
- 读代码、复跑测试：只在 `~/.cache/claude-review/` 里，只读；不碰用户的工作副本。

## 通道

```bash
~/.claude/skills/cg-link/cg.sh <ask|check|interrupt|list> '<json>'
```

| 工具 | 输入 | 说明 |
|---|---|---|
| ask | `{"agent":"{{BOT}}","message":"...","wait_seconds":120}` | 默认等 120 秒，最多 600；0 = 只看一眼 |
| check | `{"agent":"{{BOT}}","wait_seconds":120}` | 取上次之后的新回复 |
| interrupt | `{"agent":"{{BOT}}"}` | 停止当前轮次，对话保留 |
| list | `{}` | 已配置 / 已联系的 Bot，不发消息 |

- 字段名是 `agent`。Bash 的 timeout 要比 `wait_seconds` 长（比如等 600 秒，timeout 设 620000）。
- 消息很长时，先用 python 生成 JSON 文件，再 `cg.sh ask "$(cat file)"`，免得 shell 引号出错。
- 脚本会自动拉起本地 `bdk serve`（默认端口 4123），这样 check 才接得上之前的 ask。
- {{BOT}}同一时间只处理一条消息。ask 被拒时先 check，该停就 interrupt。
- 结果里有 `created: true` 说明名字写错了，Grok Bot 新建了一个空 Bot，要立即告诉用户。有 `earlierReplies` 的是之前没读的旧回复，按顺序看完。

{{BOT}}看不到当前对话，也看不到本地文件。每条消息都要自包含，并以「【Claude Code 指挥】」开头。

## 流程

### 1. 理解需求
- 弄清要做什么、不做什么、做完是什么样子。拿不准的问用户，不影响方向的我自己定。
- 界面类需求，先出设计稿（HTML + 截图）给用户确认，再派实现。
- 用一句话跟用户确认：「我理解的是 X，验收标准是 Y」。
- 确认仓库在 GitHub 上。本地如果有没推送或没提交的改动，先问用户，同意后再推。
- 在台账里登记。

### 2. 读代码
```bash
R=~/.cache/claude-review/<owner>/<repo>
[ -d "$R" ] || gh repo clone <owner>/<repo> "$R"
cd "$R" && git fetch origin && git checkout <基准分支> && git pull --ff-only
```
搞清楚现状、相关文件、项目约定，以及怎么构建、怎么测试。只读，不改，不推。

### 3. 拆任务、写任务单
- 拆成能独立完成、能独立验收的子任务。**默认按并行设计**：{{BOT}}可以同时开多个 cloud agent，能同时干的就一次全派出去，不要排队。
  - 并行的子任务改的文件尽量不重叠。实在要碰同一个文件的，要么合成一个子任务，要么排成先后顺序，并在任务单里写明「不要碰 X，T<编号>-<y> 在改」。
  - 有依赖的，写明「等 T<编号>-<x> 合并后再派」，并把它放在下一批里。
  - 多个需求之间互相独立的，也可以同时进行，台账里各记各的。
- 并发上限和额度未知。如果{{BOT}}回报派不出去或额度不够，就把剩下的子任务排进下一批。
- 每个子任务写一份任务单，cloud agent 拿到就能直接干，不需要再去问：

```
任务 T<编号>-<子编号>：<标题>
仓库：<owner/repo>　基准分支：<branch>　新分支：<branch 名>
目标：<要达成什么、为什么>
现状：<相关文件/函数/行为，读代码得出的事实，直接写出来>
要做的：
1. ...
不要做的：<不能动的文件/范围>
验收标准：
1. <可验证的结果>
验证（在你自己的机器上完成，结果贴进 PR 描述）：
- <测试/构建命令，如 npm test、pnpm build>：贴出输出摘要
- <行为验证，如启动应用、用浏览器走一遍某个流程、调用某个接口>：贴出截图或响应
- 每条验收标准都要对应一条证据
交付：在新分支开 PR 到基准分支，标题以「T<编号>-<子编号>」开头
```

- 发给{{BOT}}：

```
【Claude Code 指挥】派活 T<编号>
共 <n> 个子任务，<可并行 / 先后顺序>。请按派活协议，把下面的任务单原样交给 cloud agent（模型自动），派完立刻回报 agent 和分支。
---
<任务单 1>
---
<任务单 2>
```

### 4. 盯进度
- 不要干等，隔一段时间 ask 一次「T<编号> 进度？」，长任务用 ScheduleWakeup 或 /loop。
- {{BOT}}或 cloud agent 提的问题由我拍板。涉及上线部署、不可逆的数据操作、对外发布、明显花钱的，先问用户。
- 发现偏离方向就立刻纠偏，必要时 interrupt。

### 5. 审 PR（我来审，逐个审）
1. `gh pr view <url> --json title,state,mergeable,statusCheckRollup,files,body`
2. `gh pr diff <url>`：对照任务单，看完成度、有没有越界、正确性、边界情况、测试、是否符合项目风格。
3. 看证据：PR 描述里 cloud agent 贴的测试输出、截图、响应，有没有逐条覆盖验收标准，结果可不可信。
   - 证据缺了或者不够，就作为返工意见打回去，让它补跑、补证据，不要自己去跑。
   - 证据存疑、改动风险高、或者改了界面需要亲眼确认时，才在 `$R` 里 `gh pr checkout <号>`，在本地起服务、用浏览器看。
   - 只截一张报错图不算验证成功路径。要求它自己搭好依赖（假服务、测试仓库等），把成功路径完整走一遍。
4. 判断：
   - 不通过：写返工意见，写明具体文件、哪里有问题、期望改成什么、验收方式，然后发给{{BOT}}：「【Claude Code 指挥】T<编号>-<子编号> 返工：<意见>，请转给对应的 cloud agent，在同一个 PR 上修改。」修完回到这一步重审。
   - 通过：标记为通过，等这个需求的其他 PR。

不要在本地改代码去修 PR，问题一律写成返工意见交回去。

### 6. 终审、合并、汇报
- 这个需求的所有 PR 都通过后，对照第 1 步的验收标准做最终验收。
- 按依赖顺序合并：`gh pr merge <url> --squash --delete-branch`（仓库约定别的合并方式时按约定来）。会触发上线部署的，先问用户。草稿 PR 先 `gh pr ready`。
- 合并后其他 PR 冲突了：有冲突的 PR 不会触发 CI。打回给对应的 cloud agent，让它 rebase 到最新基准分支、保留已合并的改动、重跑验证，CI 绿了我再审。
- 告诉{{BOT}}「T<编号> 已合并，结案」。
- 向用户汇报：做了什么、PR 链接、验收结论、遗留问题。
- 更新台账。

## 任务台账 `~/.claude/cg-link-tasks.md`

每个需求一节。状态有：方向确认 / 读代码 / 已派 / 进行中 / 审 PR / 返工 / 已合并 / 搁置。

```
## T<编号> <标题>（<状态>）
- 需求：...
- 仓库/基准分支：...
- 验收标准：...
- 子任务：T<编号>-1 <分支> <PR> <状态> ...
- 记录：<日期> <事件>
```

开始任何工作前，先读台账接上进度。

## 维护
- {{BOT}}的协议在 `~/.claude/skills/cg-link/protocol.md`。协议改了要重新发给{{BOT}}，同时提醒用户更新它在 Grok Bot 应用里的指令。
- 桥接项目默认在 `~/.cg-link/bridge`（可用 `CG_LINK_BRIDGE` 改）。加 Bot：改其中 `bot/extensions/grokbot.ts` 的 `agents`，再 `pkill -f "serve --dir . --port 4123"`，下次调用会自动重启。
- 认证失败时，让用户运行 `! ~/.cg-link/bridge/node_modules/.bin/bdk login`。serve 的日志在 `~/.cache/cg-link-serve.log`。
